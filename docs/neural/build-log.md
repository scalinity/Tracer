# Build log: v2 scenario data and TracerNet

A running diary of the build that `docs/neural/spec.md` describes: what was done, in what order, what was found, and every call made along the way. Newest entries last. Times are US Eastern. The pull-request record is `docs/ai-teaming-log.md`; this log is the day-by-day detail behind it.

Every number this work reports comes from synthetic data with no clinical review.

## Sunday, November 8

**9:03 PM.** Started at commit `8686475` with no pull requests open. Read the spec end to end, then `AGENTS.md`, `CLAUDE.md`, `docs/architecture.md` §4, §5, §7 and §9, and every file the spec's §1 cites: `src/pipeline/evaluate.py`, `store.py`, `src/models/risk.py`, `src/generator/briefs.py`, `validate.py`, `config.py`, the configuration files and both guard tests.

**Environment.** The project venv is Python 3.14.10 on an Apple M5 Pro (18 cores, 48 GB). `pip index versions torch` lists torch 2.15.0 for this interpreter on macOS arm64, so spec §7.11 takes its first branch: torch goes into `requirements.txt` and no separate Python 3.13 venv is needed. The suite collects 599 tests. `.env` holds all three key names (only their lengths were checked). HiPerGator is reachable over SSH with the class allocation, and is held in reserve for training if the Mac is too slow.

**9:15 PM, N0.** Committed the spec. `.env.example` now names `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` and `OPENROUTER_API_KEY`. `tests/test_no_key_in_site.py` now matches OpenAI keys (plain, project, service-account and admin) and OpenRouter keys, with a look-behind so words such as "risk-adjusted" do not match; adds OpenAI's API host, TypeSafe's API host and OpenRouter's API path to the host list; and checks each of the three keys' values against every tracked file. It gained ten cases and passes, including against the spec itself. Added tasks N0 to N11 to the plan, N0 to N9 under Gate C; the plan check passes.

**A shared contract before parallel work.** N1 (schema and prompt) and N3 (simulator) are built at the same time by separate agents, so `config/scenario.example.json`, the spec's worked example, was written first and both build against it. Writing it settled five gaps in spec §4.3, recorded as assumptions:

- Disruptions with no line, route, unit or instrument target use fixed ids: `lab_station` for an unattended station, `receiving` for short staffing and scanner downtime.
- A `mixed` unit sends by tube with its tube share, otherwise by its courier route if it has one, otherwise on foot.
- One shift clock per scenario, from `receiving.shift_pattern`, governs every day, evening and night field (staffing, station emptying, courier rounds). Under `7-19` the evening values are unused.
- `response` is `none` for every disruption type except a tube line outage, and `noticed_after_min` only matters for outages.
- Tasks N10 and N11 join no gate, since the spec puts only N0 to N9 under Gate C.

**9:16 PM.** N0 merged as #49. Five agents now build in separate git worktrees, none of which may commit: N3 the simulator, N1 the scenario schema, planner, prompt and validators, N2 the OpenAI client, ledger and runner (at the highest effort, since it guards the cap), and two pieces with no dependency on the others, TracerNet's network core (bins, rungs, loss, calibration) and the evaluation harness's core. torch 2.15.0 and Optuna 5.0.0 are installed; MPS works, though CPU wins on small matrices, as expected for a network of about 0.3 million parameters.

**Docs check before any API code.** All three model ids exist and the prices match the spec, with Batch and Flex at exactly half of Standard in every column. Three findings change the client: under OpenAI's default implicit caching a one-off prompt is billed at the cache-write rate (1.25 times input), so only the stable developer prefix earns its write back; Flex's capacity error is a 429 with no machine-readable code; and exhausted credit arrives as `credit_balance_exhausted`. The project must also allow the Flex tier, or every Flex request fails with a 400.

**HiPerGator.** The class allocation is 8 GPUs, 32 CPUs and 250 GB shared by the whole class. A 0.3-million-parameter network is limited by building its inputs, not by GPU arithmetic, so training starts on the Mac (18 cores) and HiPerGator is the fallback for running search trials or ablations in parallel.

**9:23 PM, the plan.** The first republish was refused: the published plan held a November 8 rework (tasks R1 to R7, a rework summary, a new API section) that was never committed. Main's plan is now rebuilt from the published page, with N0 to N11 added after R7; overwriting the page would have erased the rework.

**9:49 PM, N1.** The evaluation harness core landed first (59 tests; its vectorized scores and bootstrap reproduce `evaluate.py` exactly on the v1 held-out runs), then TracerNet's core (28 tests; 150,893 parameters at rung A and 317,901 at rung C, against the spec's 0.15 and 0.31 million). Both wait on their branches for the N6 and N7 pull requests. N1 merged next: the schema, planner, prompt, validators and signatures, 402 tests. The developer message is about 8,200 tokens, longer than the spec's 6,500 estimate, and is the same for every job and model so one cached prefix serves the run. Before merging, the message was checked for every denylisted institution name.

**10:14 PM, N2.** The client, ledger and runner landed. The O1 dry run builds the 72 real pilot requests (24 briefs on each of `gpt-6-luna` at low effort, `gpt-6.1-terra` at low and `gpt-6.1-sol` at medium) and prices them at $2.03 expected and $5.05 worst case against the $3.00 cap, sending nothing; requests the cap cannot cover are refused, never sent. Wiring found two problems before any money moved: the validator's layer names did not match the runner's, which would have paid for repairs of near duplicates, and the job configuration split the pilot by the main run's stratum shares instead of six per stratum.

**The simulator, second pass.** Feeding N1's code-random scenarios through N3's engine found specimens still sitting at their unit at the 7,200-minute horizon (a unit whose dispatch time has a median of 2 minutes and a 90th percentile of 170 has a very long tail). They produced invalid trails and would have dropped whole replicates. By the spec's definition such a specimen is never received, so it now ends open-ended, flagged `horizon_cut`. The plausibility check now simulates the full week instead of two days, since a two-day check never sees a disruption planned for later in the week; at 0.11 seconds per check the cost is negligible.

**10:18 PM, N3.** The simulator merged with its fixes (#53). Earlier entries' times are now taken from the commit history; the first drafts of three of them were estimates and ran up to 1 hour 40 minutes ahead of the clock.

**10:20 PM, pilot O1.** The first run stopped after 45 seconds on a seam the fakes never exercised: the runner passes a repair's reasons as a list, and the prompt expected one string. Nothing was lost. The 12 requests in flight had all completed, and their raw responses were on disk before the crash, so the resume settled each from its stored usage instead of keeping its worst case; no request was sent twice. After a one-line fix and a test through the real planner and prompt, the resume finished in 96 seconds: 69 of 72 brief-model pairs accepted, 7 repairs, 3 dropped, $0.60 of the $3.00 cap.

**The gate.** Every model passed G1 to G6. Real requests use about 10,500 input tokens (the dry run's local estimate was twice that) and 1,500 to 3,900 output tokens, so every model cost about half its estimate: `gpt-6-luna` low $0.0008 per accepted scenario, `gpt-6.1-terra` low $0.0072, `gpt-6.1-sol` medium $0.0175. Terra is the cheapest model within 5 points of the best on acceptance (96% against 100%) and adherence (100%); Luna was 8 points behind on acceptance. For the edge stratum the rule reads adherence on the edge briefs themselves, where Luna met 5 of 6 (83%) and Terra all 6, so Terra writes every stratum of the main run. The spec's count formula, floor($44 x 0.95 / $0.00715), gives 5,846 accepted scenarios, about 2.6 times the spec's planning figure of 2,250; the formula is followed as written, and the cap stops spending in any case.

**10:33 PM to 11:20 PM, the review.** Before the main run, the spend code went to a reviewer from another vendor (GPT-6.1 Sol, read-only). It came back with four critical defects. The sharpest: every Flex request was reserved at Flex rates, so a request billed at Standard could overshoot, and its probe took the pilot's job from $2.94 to $3.02 against a $3.00 cap. Others: a server error was voided and retried though it may have been billed; a Batch job whose creation timed out could be submitted twice; a reservation made before a crash was reused at its old size. All eleven findings are fixed and tested. Reservations are now at Standard rates, and input is bounded by the request's bytes, which a tokenizer cannot exceed (a typical main-run request reserves $0.138 against about $0.007 billed). The main run waited for the fixes; no money was at risk in the meantime, since the pilot had finished with nothing held.

**11:42 PM, a secondary analysis, fixed before any real validation or test result exists.** The evaluation driver's smoke check on the 8-scenario development set showed the headline metric collapsing: at 6 alerts per shift, the median warning over all breaches (a miss counting as zero) was 0 for almost every method, because those laboratories have more breaches per shift than the budget has alerts. The real library spans 30 to 900 specimens a weekday, so its large laboratories will have 10 to 25 breaches per shift against 6 alerts, and the pooled median may be 0 for every method, so R1 could fail by construction whatever the network does. The pre-registered rule of spec §8.6 stays binding exactly as written and the test set is still scored once. Added beside it, and labeled non-binding: R1 to R3 recomputed at 30 alerts per 100 specimens (one of the spec's own budgets, §8.3), with the same margins and intervals, plus the capped mean warning at every budget. This is decided now, before the real validation set has been scored, so it cannot have been chosen to favor any method.

## Monday, November 9

**11:23 PM to 1:01 AM, the main run (O2).** `gpt-6.1-terra` at low effort wrote one laboratory week for each of 6,101 briefs on the Flex tier, through the ledger. 5,137 passed every check on the first try; 963 were repaired once, and 886 of those passed. 6,023 were accepted (98.7% of the briefs), 52 failed twice and were dropped, and 26 requests were never sent: when about $0.13 was left under the $44.00 cap, a request's worst-case reservation (about $0.138) no longer fit, so the ledger refused them, as it should. The job spent $43.8659; OpenAI's total for the project is now $44.4662 of $76.43.

**What the repairs show.** Almost every repair was a "normal" week. Terra's normal weeks simulate to breach shares of 11% to 24%, above the normal band of 0.3% to 10% the plausibility check enforces, so normal briefs passed on the first try 64.5% of the time against 92% to 99% for the other strata. Repairs recovered nearly all of them (2,069 of 2,136 normal briefs accepted), but the gap is real: the model's sense of an ordinary week runs hotter than the simulator's. It is a candidate for the round-2 weak-spot job.

**1:02 AM, the ledger against OpenAI's usage page.** The page showed $43.27, 72.2 million input tokens and 7,386 requests; the ledger holds $44.47, 74.9 million input tokens and 7,117 settled requests. The page had 97.3% of the dollars and 96.4% of the tokens, the same lag in both, so the gap ($1.20) is the page catching up on the last minutes of the run, not a price disagreement. At 1:20 AM the page showed $44.98 for November against the ledger's $44.47: $0.51 (1.2%) apart, inside the $1 and 5% limits. The page's extra requests are Flex refusals, which carry no tokens.

**1:12 AM to 1:16 AM, the freeze.** The first attempt re-validated the 6,092 accepted scenarios one at a time (each check simulates a full week), which would have taken about half an hour on one core; it was stopped before writing anything and the re-validation now runs in worker processes. Every scenario passed again. 21 near duplicates were left out, leaving 6,071 scenarios in 5,396 families: train 3,668, validation 772, test 782 and out-of-distribution test 849. Coverage holds in every cell, factor level and edge tag. The library is far less spread out than code-random scenarios (a Vendi score of 73 on 2,000 against 1,974), as expected from a model writing plausible laboratories rather than uniform noise.

**The out-of-distribution set.** A family goes to `test_ood` whole if any member is a multi-site system or has a scanner outage. Union-find at 1.5 times the near-duplicate distance chains some dense regions into large families (the largest has 147 scenarios), and each of the six largest holds an out-of-distribution member, so 367 of the 849 `test_ood` scenarios are ordinary weeks that travel with their family. That keeps near-identical weeks out of two splits, which is the point of families; the report will give `test_ood` results on the 482 scenarios that carry the feature as well as on the whole set.

**12:21 AM to 12:41 AM, putting N6 together.** Two agents built store v2, the observed-only feature builder, TracerNet's network and the evaluation driver in separate worktrees; they were merged on one integration branch, where the full suite passed (1,393 tests). Three seams needed fixing: the store did not read a frozen record's ids from its `meta` block, a feature schema read back from disk ordered its series alphabetically (which the network refuses), and nothing produced TracerNet's risk table for the driver, so `evaluate --artifact` now scores a set with the trained artifact first.

**Two slow layers.** The agent building training measured rung B at about 727 samples a second on CPU against 53,000 on the Apple GPU. A profile found two culprits in PyTorch's CPU code: the dilated causal convolution takes a slow path (and slows down with more threads), and the backward pass of a 1x1 convolution loops over the batch. Both are now the same arithmetic written as shifted slices and one `einsum`, with the same parameters and outputs equal to about 1e-6. One process now scores about 25,000 ticks a second on CPU, roughly 13 times the previous four-process rate. That matters because final test scoring runs on CPU to be bit-reproducible.

**12:43 AM to 12:52 AM, an independent review of the evaluation's integrity.** GPT-6.1 Sol (read-only) checked the test lock, truth isolation, label-free knob tuning, the decision rule and validation-only training. Truth isolation held, and the decision rule matched the spec. It found four critical defects: TracerNet could score a test set before the lock was taken; the lock's fingerprint left out inputs that change reported numbers (which risk table, the urgency weights, the training store); store and artifact manifests were trusted without checking the files against them; and knob tuning could return a threshold whose history volume exceeded the budget (47.6 alerts per shift against 6 in its probe). Four warnings followed: R4's matched-volume check ran only when asked, the worker cache key sampled the data, rung selection could keep B or C with its warning check unrun, and the predictor tuned one knob across scenarios.

**12:52 AM to 1:33 AM, the fixes.** An Opus agent fixed all eight, each with a test shown to fail on the old code (18 tests). The lock is taken before any test inference and reused; it covers every input that changes a number; files are verified against their manifests; v2 tuning has a no-alert knob, so a budget is never exceeded; R4's sensitivity runs whenever R4 fails; the cache key is a full digest; selection refuses to finish without its warning check; and the predictor tunes per scenario on history alone. The `legacy_v1` set still reproduces `results/evaluation.json` exactly.

**What the strict budget means.** In a laboratory with more breaches per shift than the budget has alerts, every method whose risk reaches 1 at the window's close (all of them) has no knob that both alerts and stays in budget, so it alerts on nothing there. Before the fix those scenarios ran over budget without anyone seeing it. The evaluation now counts them per method and budget, and the report states the counts beside R1.

**1:24 AM to 1:31 AM, store v2.** 20,616 simulated weeks became `data/store-v2/`: 48.9 million specimens and 228 million scan events in `observed.duckdb` (3.7 GB), and the truth in a separate `truth.duckdb` (7.7 GB). Only the observed file was copied to HiPerGator for training (verified by SHA-256); the truth never leaves this Mac.

**Memory.** A three-minute training benchmark on the real store pushed this Mac to 44 of its 45 GB of swap: the training table and its twelve feature workers held about 20 GB beside everything else the Mac was running. It was stopped. Training runs on HiPerGator, where a job can ask for 100 GB; this Mac keeps the evaluation and the CPU scoring.

**The re-review, and a defect real data found.** Sol's second pass closed five of the eight findings and raised five narrower warnings: a recorded test run could still score a different artifact or store, the lock did not record which risk-table column was read, a separate training store without a manifest had no identity, the predictor applied the v2 no-alert knob to v1 tuning, and harm clipped invalid probabilities instead of refusing them. All five are fixed with tests. The first validation run on the real store then stopped on its own new check: the locally refit analytic model gave a risk that was not a number. A history week with no never-received specimen fits a mixture whose never-received share is 0, so a specimen silent past both of its components gets 0/0. Such a scenario now uses the global fit for its history and scored weeks alike, as spec §8.2 says to do when a refit fails, and the note says why (4 of the 772 validation scenarios).

**The Mac stopped responding.** The first validation run held about 12 GB beside everything else the Mac had open, and the Mac stopped responding and had to be restarted. Nothing on disk was lost. After the restart the Mac's own applications used about 44 of its 48 GB, so it now does only git, pull requests and quick tests; evaluation, training and the test suite run on HiPerGator, with the truth file in an evaluation-only folder that no training job reads.

**2:51 AM to 3:16 AM, the validation baselines.** On a 24-CPU HiPerGator node: 772 scenarios, 4.09 million scored specimens and 305,080 breaches over 48,636 shifts, 25 minutes. At 6 alerts per shift every baseline's median warning over all breaches is 0: these laboratories average 6.3 breaches per shift, more than the budget has alerts, and in 261 of the 772 scenarios the window rule and the equally weighted analytic models have no knob that both alerts and stays within budget (13 with the 3-2-1 or 9-3-1 weights, where high tiers outweigh the rest). The capped mean warning still separates them: the locally refit analytic model with 3-2-1 weights gives 13.0 minutes, the window rule 7.2. At 30 alerts per 100 specimens every scenario has a feasible knob, the analytic models and the window rule catch 88% to 100% of breaches, and the capped mean warning runs from 44 to 56 minutes for the analytic models against 48 for the window rule. These are validation numbers for the baselines; nothing has been scored on a test set.

**Byte-for-byte checks across processors.** On HiPerGator's AMD processors, four tests that regenerate committed v1 results exactly fail; the same three fail on the unchanged main branch there, and all four pass on the Mac where those files were made. Floating-point results differ in the last bits between the two processors, so the exact-regeneration checks are run on the Mac and the rest of the suite on HiPerGator.

**6:59 AM, analyses for a possible paper, fixed before any test result exists.** This work may become a paper, and two gaps would draw a reviewer's first objections: no one has judged whether the scenarios look like real laboratories, and every result comes from one simulator written for this project. Spec §8.11 now fixes two analyses for them, both non-binding. The first re-simulates the test families in five perturbed worlds (heavier-tailed durations, disruption effects halved and doubled, every duration 20% faster or 25% slower) and scores the frozen methods on each after `test` is locked, calling each world consistent or sensitive by a rule written now. The second is an optional blinded plausibility rating of 15 library scenarios against 15 code-random ones, run only if Karissa agrees, outside this build. Any other analysis of the test sets is labeled exploratory. The rule of §8.6 is unchanged, no test set has been scored, and nothing here spends API money.

**3:19 AM to 4:00 AM, the search.** Optuna searched rung B's settings on one B200 GPU: 24 trials, 15 finished and 9 stopped early by the median rule, none failed. The best, trial 21, reached a validation score (`val_sel`, lower is better) of 0.08750 with a learning rate of 4.99e-3 (the top of its range), weight decay 1.21e-4, dropout 0.281, width 128, 48 temporal channels, λ 2, η 0 and batches of 2,048; these are `search.best` in `config/neural.yaml`, and `results/neural/hpo.json` holds every trial. The search's first launch ran out of memory holding two copies of the feature table, so two plain workers shared one journal file instead; the second never got CPUs before the deadline.

**4:06 AM to 4:58 AM, the ladder.** Each rung trained once (seed 0) with the searched settings and no time box. L on CPU: best `val_sel` 0.09188 in 974 s. A on CPU: 0.08347 in 2,690 s. B on a B200: 0.08340 in 851 s. C on a B200: 0.08245 in 1,144 s, still improving at its 30-epoch cap. Epochs ran 31 seconds rather than the spec's 10 minutes, because the start-up speed check measured feature building at 4,144 samples a second against about 80,000 in a real run; commit 4c44858 resizes the epochs after the first one. The ladder stands as run, since every rung trained under the same rule, and the final ensemble uses the fix. `results/neural/runs.csv` has one row per run (the search's trials and the ladder; the four speed benchmarks are left out).

**5:06 AM to 9:36 AM, rung selection.** Spec §7.9's rule picks C: its `val_sel` is the lowest, and B is 1.15% behind, outside the 1% tolerance that would favor the simpler rung. Its warning check compares C's validation median warning (6 alerts per shift, all breaches, a miss counting as zero) with A's: both are 0.0 minutes, so C is not more than 5 minutes behind and stays. Getting that number took three runs. The first scored validation for 2.5 hours, mostly in its evaluation pass, where every scenario group re-read the whole 484 MB risk table and each of about 30 workers ran a 64-thread Polars pool on 64 cores: it used a third of its cores, 42% of that time in the kernel, and after memory kills it hung and was cancelled at 7:32 AM. Commit 42caffc makes each lookup read only the risk parts that can hold its specimens, starts every worker with one thread per library, sizes pools from the scheduler's CPU set, and writes a progress file the monitor reads. The second run then started all 63 evaluation workers at once, about 7 GB each, and crossed its 450 GB limit 53 seconds in; with 700 GB the third run finished in 70 minutes. `results/neural/selection.json` is its record.

**9:39 AM to 11:54 AM, artifact v1 and the validation evaluation.** The first try ran calibration's forward passes on one core, because the job script still gave the main process one thread, which the workers no longer need after 42caffc; it was cancelled after 21 minutes with nothing written and rerun with 32 threads. Artifact v1 (`artifacts/tracernet/v1/`, 1.72 MB) is rung C's seed-0 run, calibrated on 3 million validation ticks; N8 replaces it with the three-seed ensemble trained with round two's scenarios. On validation, which does not bind and flatters the network since its rung was chosen there:
- R1 fails: every method's median warning at 6 alerts per shift is 0.
- R2 holds: TracerNet alerts on more never-received specimens than every baseline.
- R3 holds: Brier 0.047 against the better analytic refit's 0.077 at 30 minutes, 0.032 against 0.043 at 60.
- R4 fails against the window rule alone, which spends 3.75 alerts a shift against TracerNet's 5.85; both analytic refits are within 10%.

The capped mean warning at 6 alerts per shift with the 3-2-1 weights is 22.5 minutes against 13.0 for the locally refit analytic model (difference 9.5, 95% interval 8.7 to 10.2). At 30 alerts per 100 specimens the median warning is 55 minutes against 50 (difference 5, interval 0 to 10). AUROC at 30 minutes of silence is 0.955 against 0.914, and AUPRC 0.861 against 0.594. These are synthetic laboratories with no clinical review, and the test families, scored once in N8, decide the claim.
